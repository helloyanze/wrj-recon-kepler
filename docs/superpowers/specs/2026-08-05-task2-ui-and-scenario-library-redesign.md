# 任务二界面复用与演示场景库扩展设计

日期：2026-08-05

## 1. 背景

任务二动态重规划演示已经具备三维地图、事件播放、计划切换和七步决策过程，但当前界面存在四类问题：

- 左侧图层、颜色和航迹设置没有复用任务一已经验证的交互方式，多组滑杆和颜色项同时展开，信息冗余。
- 左侧直接展示内部变化类型、资源状态和任务状态，仍有裸英文代码。
- 右侧决策过程的主要字体只有 8–11px，候选方案只给状态和少量指标，没有说明处理了哪些数据，也没有用数据解释接受或拒绝原因。
- 场景库只有四个基础案例，无法完整展示任务变化、事件治理、多任务依赖和多候选排序。

本设计同时覆盖两个仓库：

- `wrj-t2`：构建多任务演示基线、扩展场景定义并通过真实任务二流程导出结果。
- `wrj-recon-kepler-demo`：接入场景、复用任务一图层交互并重做中文决策展示。

## 2. 目标与非目标

### 2.1 目标

- 让任务一和任务二共享稳定的图层操作习惯，不改变两者各自的数据模型。
- 将任务二主要操作和结论全部中文化，原始代码只在工程审计详情中出现。
- 右侧按照“结论 → 原因 → 方案数据 → 对比证据 → 审计详情”解释每个候选方案。
- 所有结论都由实际场景数据支撑；没有的数据明确显示“暂无记录”。
- 将演示场景扩展为九个，覆盖资源事件、任务事件、事件冲突和综合贯穿案例。
- 明确区分演示构造输入、任务二实际计算结果和正式验收数据。
- 保持任务一现有行为、任务二地图播放和详情抽屉不回归。

### 2.2 非目标

- 不实现用户在前端编辑事件并现场运行 Python 算法。
- 不把任务二数据压缩成任务一 `CaseBundleV2`。
- 不加入技术方案已排除的动态禁飞区、实时天气、运动目标高频跟踪等能力。
- 不在前端手工编写或修改算法输出 JSON。
- 不用文档中的预期数值覆盖任务二程序的实际计算结果。

## 3. 设计原则

1. **复用交互，不混合业务模型。** 任务一和任务二共享图层行、折叠编辑器等界面原语，各自保留偏好设置和地图图层语义。
2. **先结论，后证据。** 外行先看到明确结论，再看到支撑结论的数据，最后才查看内部编号和代码。
3. **数据优先于文案。** 接受、拒绝、未胜出和安全回退必须由真实字段生成，不能用固定宣传文案代替。
4. **渐进披露。** 关键摘要默认可见，工程审计按需展开。
5. **演示数据可追溯。** 场景由任务二导出器生成，记录输入性质、提交号、生成时间和哈希。
6. **场景必须有可观察变化。** 只有确实改变任务、资源、工作单元、航迹、时间链或裁决结果的场景才进入目录。

## 4. 左侧“图层与航迹”设计

### 4.1 布局与交互

任务二左侧改为与任务一一致的折叠式图层栏：

- 标题统一为“图层与航迹”。
- 标题栏保留“恢复默认”和整体收起按钮。
- 每一行依次显示图例色块、中文图层名和显隐按钮。
- 一次只展开一个图层；默认展开“调整后航迹”。
- 透明度、线宽、颜色等设置只在图层展开后出现。
- 删除底部“资源”和“任务”对象列表；地图点选和详情抽屉继续承担对象查看职责。

任务一与任务二共享以下无业务状态的基础控件：

- 图层行与显隐按钮；
- 图层图例色块；
- 折叠编辑区域；
- 颜色输入；
- 透明度和线宽输入；
- 恢复默认及收起按钮样式。

任务二仍单独维护 `DynamicLayerPreferencesV1`、场景级本地存储、变化类型和资源颜色，不复用任务一的偏好数据结构。

### 4.2 图层与颜色

任务二保留六类图层：

- 任务区域；
- 工作单元；
- 原计划航迹；
- 调整后航迹；
- 无人机位置；
- 事件位置。

“调整后航迹”展开区保留“按变化类型 / 按无人机”切换。变化类型只显示当前场景实际出现的项，并使用以下中文名称：

| 原始值 | 主界面名称 |
| --- | --- |
| `baseline` | 原计划 |
| `baseline_locked` | 锁定保留 |
| `baseline_reused` | 沿用原航迹 |
| `dynamic_modified` | 动态调整 |
| `dynamic_new` | 新增航迹 |
| `dynamic_cancelled` | 已取消航迹 |

无人机默认显示“1号无人机”之类的中文别名；原始编号放在次要文本或审计详情中。主界面不再单独重复展示一套颜色图例。

## 5. 右侧决策过程设计

### 5.1 可读性与信息层级

- 常规桌面宽度下，右侧面板目标宽度约 420px；空间不足时可收缩到约 380px。
- 正文不小于 13px，候选标题约 15px，关键结论约 16px。
- 工程审计可以使用较小字号，但主要结论、原因和数据不得使用现有 8–10px 字号。
- 七步流程继续作为导航；当前步骤下方按“输入数据 → 处理结果 → 决策结论”组织内容。

### 5.2 七步与模块对应

| 前端步骤 | 中文名称 | 对应模块 |
| --- | --- | --- |
| `EVENT_INGESTION` | 接收并治理动态事件 | T2-M01、T2-M03 |
| `SNAPSHOT_AND_IMPACT` | 冻结快照并分析影响 | T2-M02、T2-M04 |
| `RESOURCE_ASSESSMENT` | 评估资源与安全状态 | T2-M05 |
| `CANDIDATE_GENERATION` | 生成分层候选方案 | T2-M06 |
| `PLANNING_AND_VALIDATION` | 规划、合并并校验 | T2-M07、T2-M08、T2-M09、T2-M11 |
| `RANKING_AND_SELECTION` | 排序并选择方案 | T2-M10 |
| `PLAN_PUBLICATION` | 发布新版本和增量结果 | T2-M12 |

每个步骤默认展示与该步骤有关的实际数据，例如事件类型和时间、快照编号、受影响任务与资源、剩余油量、候选数量、校验数量、计划版本和差异数量。

### 5.3 候选方案展示模型

原始 `decisionTrace`、`missionView` 和 `planDiff` 先转换为纯展示模型，再由组件渲染。展示模型至少包含：

- `title`：方案 A、B、C 等用户可读名称；
- `strategyName`：最小调整、单机替换、备份机接替、多机协同或安全回退；
- `verdict`：接受、拒绝、可执行但未选中、安全回退；
- `verdictReason`：由候选生命周期、失败码、排名和选择原因生成；
- `planDataRows`：任务、资源、工作单元、航迹变化和关键指标；
- `evidenceRows`：支撑结论的阈值、校验或与胜出方案的差异；
- `auditRows`：原始候选编号、阶段代码、失败码、校验编号和对象 ID。

候选卡固定采用以下顺序：

1. 方案结论；
2. 结论依据；
3. 方案处理数据；
4. 针对性对比证据；
5. 可展开的工程审计详情。

主界面方案名称映射：

| 原始层级 | 中文名称 |
| --- | --- |
| `L1_MINIMAL_ADJUSTMENT` | 最小调整 |
| `L2_SINGLE_REPLACEMENT` | 单机替换 |
| `L3_STANDBY_LAUNCH` | 备份机接替 |
| `L4_MULTI_RESOURCE` | 多机协同 |
| 回退候选 | 安全回退 |

已知失败原因至少覆盖：

| 原始代码 | 中文说明 |
| --- | --- |
| `INSUFFICIENT_REMAINING_FUEL` | 剩余油量不足 |
| `HARD_DEADLINE_MISSED` | 无法满足硬截止时间 |
| `E503_PARTIAL_SAFE_FALLBACK` | 完整目标无法满足，已形成安全回退 |

通过校验但未选中的方案必须说明“方案可执行，但在字典序比较中低于胜出方案”，并展示首次产生差异的指标。选中方案必须说明通过了哪些校验、排名为何第一。安全回退必须列出未满足目标和实际保住的安全结果。

未知代码在主界面显示“未识别的工程原因”，审计详情保留原始值，避免裸英文渗透到主要叙事。

### 5.4 数据缺失规则

- 数据源未提供的数值显示“暂无记录”，不得估算。
- 失败码只有定性结论、没有阈值时，只显示已有资源数据和校验结论。
- 文档预期与任务二实际输出不一致时，主界面展示实际输出；文档值仅可作为场景设定或验收目标。

## 6. 场景库设计

### 6.1 场景清单

场景库扩展为九个：

| 分组 | 场景 ID | 中文名称 | 核心展示 |
| --- | --- | --- | --- |
| 基础案例 | `resource-lost` | 无人机失联 | 资源失效与任务转移 |
| 基础案例 | `low-fuel-return` | 低油量返航 | 油量安全判定与返航 |
| 基础案例 | `new-area-task` | 临时新增侦察区 | 新任务、工作单元和航迹生成 |
| 基础案例 | `hard-deadline-fallback` | 硬截止无法满足 | 候选失败与安全回退 |
| 任务变化 | `task-cancelled` | 执行中任务取消 | 保留已完成事实并释放未来工作 |
| 任务变化 | `task-priority-raised` | 已有任务优先级提升 | 多任务顺序和资源分配调整 |
| 任务变化 | `task-dependency-changed` | 任务依赖关系改变 | 前后置约束和时间链变化 |
| 事件治理 | `event-conflict-resolution` | 多事件冲突消解 | 同对象区域变化与取消冲突时，取消优先 |
| 综合案例 | `comprehensive-multi-event` | 多事件综合重规划 | 贯穿 12 个模块的完整闭环 |

### 6.2 多任务演示基线

现有任务一正式算例均为单任务，无法真实展示优先级和依赖关系变化。因此 `wrj-t2` 增加一套可追溯的多任务演示基线，基于用户提供的《任务二_模块总体设计与贯穿案例说明文档》建立：

- 任务 T-A、T-B，以及综合场景中动态新增的 T-C；
- 无人机 U1–U4；
- T-A 与 T-B 的区域、时间窗和依赖关系；
- 无人机阵地、能力、油量和准备时间；
- 可供快照还原的航迹、工作单元和运行状态。

基线必须通过任务二冻结契约校验，并明确标注为演示构造输入。它不能被描述为实飞数据或正式验收原始输出。

### 6.3 四个专项新增场景

1. **执行中任务取消**：取消仍有未来工作的任务；断言已完成前缀保留、未来工作单元取消或释放、相关资源不再执行被取消任务。
2. **已有任务优先级提升**：提高一个已有任务的优先级；断言任务次序、资源分配或完成时刻至少一项发生可观察变化。
3. **任务依赖关系改变**：为两个已有任务新增或调整前后置关系；断言时间链满足新依赖且不存在依赖环。
4. **多事件冲突消解**：同一任务同时发生区域变化和取消；断言取消优先，区域变化保留审计记录但不进入最终规划状态。

如果某个场景只改变字段而没有产生可观察的任务、资源、航迹、时间链或裁决变化，则导出测试失败，该场景不得发布。

### 6.4 综合贯穿案例

综合案例使用文档中的任务、资源和事件逻辑：

- U1 低油量；
- T-A 区域扩大；
- 重复的区域变化事件；
- T-A 截止时间两次修改并采用最新值；
- 新增高优先级任务 T-C；
- U2 延迟到位；
- T-B 受 T-A 变化间接影响。

界面重点展示：

- 7 条原始事件归约为 5 条有效变化；
- 重复事件被忽略、旧截止值被覆盖的原因；
- U1 的实际剩余油量、立即返航需求和完成当前条带后需求；
- L1–L4 候选的预检查、详细规划和淘汰链；
- 两个有效候选的任务时间、计划保留率和油耗比较；
- 字典序在首次不同指标处停止比较的选择逻辑；
- 计划版本递增及发布结果。

文档中的 13.8kg 等原始状态值在契约允许时作为场景输入。12.6kg、14.7kg、72%、65% 等派生结果只作为解释性预期，不是固定验收阈值。场景验收关注“立即返航是否安全”“候选是否因数据被淘汰”“字典序是否选择首次优势方案”等业务关系；最终界面必须展示任务二程序实际输出，不能为了匹配文档而在前端覆盖结果。

### 6.5 场景目录元数据

场景目录升级为版本 3，并为每个场景增加：

- `category`：`foundation`、`task_change`、`event_governance` 或 `comprehensive`；
- `dataNature`：固定为 `SIMULATED_PIPELINE_RESULT`，中文显示“演示构造输入 · 任务二实际计算”；
- `featured`：是否为综合旗舰场景。

前端加载器兼容版本 2 和 3；版本 2 使用默认分组，版本 3 直接按元数据生成中文分组。场景归属不得硬编码在 React 组件中。

## 7. 跨仓库数据流

```text
任务一真实输出 / 多任务演示基线
              +
任务二动态事件与运行状态
              ↓
wrj-t2 真实重规划流程
              ↓
mission_view.v1 + decision_trace.v1 + failure_report? + provenance
              ↓
wrj-t2 场景导出器与业务断言
              ↓
前端 prepare-task2-scenes 校验并复制
              ↓
DynamicScene 构建与展示模型转换
              ↓
左侧图层控制 + 地图播放 + 右侧中文决策证据
```

生成资产只允许通过导出和准备命令更新。`provenance.json` 继续记录任务二提交号、生成命令、生成时间、输入输出哈希和模拟数据性质。

## 8. 模块边界

### 8.1 `wrj-t2`

- 多任务演示基线构建器：只负责生成满足冻结契约的演示输入。
- 场景定义：声明事件批次、演示时刻、预期状态和镜头目标。
- 场景业务断言：验证每个案例的核心可观察结果。
- 场景导出器：运行真实管线、校验输出、写入来源记录和目录。

### 8.2 前端展示层

- 共享图层控件：无业务状态的任务一/任务二共用组件。
- 任务二侧栏适配器：把动态偏好和场景变化类型传给共享控件。
- 决策展示转换器：把任务二原始代码和数据转换为中文展示模型。
- 决策过程组件：只渲染展示模型并处理步骤导航。
- 场景目录与选择器：解析版本 2/3 元数据并按中文分组显示。

地图图层、播放状态机、时间轴和详情抽屉继续使用现有边界，除适配新场景数据外不做无关重构。

## 9. 错误与降级处理

- 单个场景缺失、哈希错误或契约校验失败时，将该场景标记为不可用并显示中文错误，其他场景仍可选择。
- 目录版本、场景版本或数据性质未知时拒绝静默猜测，提供明确错误。
- 未识别的阶段、候选层级、状态或失败码使用中文兜底说明，并在审计详情保留原始值。
- 候选没有指标时仍显示涉及任务、资源、校验结果和拒绝原因；缺少字段显示“暂无记录”。
- `PARTIAL_SAFE_FALLBACK` 必须与 `COMPLETE` 在标题、颜色和结论上明确区分。
- 综合案例实际输出偏离文档解释性预期时，不篡改输出；只有业务关系断言失败才阻止发布，数值差异由来源说明记录。

## 10. 测试策略

### 10.1 `wrj-t2`

- 场景定义测试：九个场景顺序、中文名称、分组、事件类型和预期状态正确。
- 多任务基线契约测试：任务、资源、依赖、工作单元、航迹和引用闭合。
- 场景结果测试：取消、优先级、依赖、冲突消解和综合场景分别满足业务断言。
- 导出测试：九个场景均生成有效任务视图、决策追踪、来源记录和可选失败报告。
- 决定性测试：相同输入重复导出的关键业务内容一致。
- 哈希和规范化 JSON 测试：输出可追溯且不可被手工静默修改。

### 10.2 前端

- 目录 Schema 测试：兼容版本 2/3，版本 3 分组和数据性质解析正确。
- 场景加载测试：九个场景均能构建 `DynamicScene`。
- 展示转换器测试：阶段、事实、候选层级、生命周期、失败码和选择原因中文化。
- 候选证据测试：接受、拒绝、未胜出和安全回退都有方案数据与原因。
- 主界面语言测试：已知裸英文代码不出现在主要展示区；审计详情仍可追溯。
- 侧栏交互测试：折叠、显隐、透明度、线宽、颜色模式、场景相关颜色和恢复默认正确。
- 任务一回归测试：任务一图层、颜色、航迹设置及其测试保持通过。
- 播放回归测试：九个场景可播放、暂停、拖动、跳步和重新播放。

### 10.3 视觉验收

- 在常用桌面分辨率下检查约 300px 左栏、380–420px 右栏与地图剩余空间。
- 确认主要文本字号、行高、候选卡数据密度和审计折叠可读。
- 检查全部九个场景的中文标题、状态、结论和数据性质标识。
- 检查长编号和未知代码仅在审计详情中换行，不撑破布局。

## 11. 验收标准

- 场景选择器按中文分组展示九个可用场景。
- 所有场景均由任务二导出流程生成并可追溯，前端无手工算法结果。
- 左侧采用任务一式折叠交互，资源/任务重复列表被移除。
- 调整后航迹颜色仅显示当前场景实际出现的中文变化类型。
- 右侧主要正文不小于 13px，候选卡按照既定五层结构展示。
- 每个候选方案都有明确结论、原因和实际方案数据。
- 选中方案解释为何胜出；拒绝方案解释为何淘汰；可执行未选中方案展示与胜出方案的首次指标差异。
- 工程审计详情保留原始编号、代码、校验和对象 ID。
- 综合案例展示文档贯穿案例的数据链和 12 个模块对应关系，并明确标识模拟数据性质。
- 任务一现有行为及全部相关测试无回归。

5. 抽取任务一/任务二共享图层控件并完成两侧回归。
6. 建立决策中文展示模型和候选证据计算。
7. 重构右侧组件、样式和综合案例模块映射。
