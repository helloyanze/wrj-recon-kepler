# 任务二动态重规划前端演示设计

日期：2026-07-30

## 1. 背景

`wrj-t2` 已提供任务二动态重规划内核，并将
`mission_view.v1.json` 定义为前端唯一固定解析入口。该投影包含任务、资源、工作单元、
分配、航迹、事件、方案差异、指标、校验结果、备选方案摘要、时间链和来源信息。

`wrj-recon-kepler-demo` 已具备任务一静态规划的算例加载、三维地图、无人机动画、时间轴、
图层控制、详情抽屉和本地导入能力。本设计在不破坏任务一既有模型与功能的前提下，在同一
工作台内增加任务二动态重规划演示。

## 2. 目标

- 在同一工作台内切换“任务一静态规划”和“任务二动态重规划”。
- 使用任务二真实运行结果制作稳定、离线可用的预制场景。
- 明显展示“基线执行、事件发生、影响分析、重规划、方案切换、新方案执行”。
- 首批交付四个场景：无人机失联、低油量返航、临时新增侦察区、硬截止无法满足。
- 支持自动播放、暂停、拖动和重新播放。
- 复用现有三维地图、无人机、时间轴和详情抽屉能力。
- 保留任务二事件、差异、计划状态与来源追溯信息，不将其压缩成任务一模型。

## 3. 非目标

- 本阶段不从浏览器现场调用 Python 或任务二服务。
- 本阶段不实现用户编辑事件并现场运行算法。
- 本阶段不修改任务一 `CaseBundleV2` 的数据契约。
- 本阶段不展示备选方案的完整航迹，只展示任务二已输出的摘要。
- 本阶段不为纯 `FAILED` 尝试制作可播放地图场景；任务二当前只保证这类尝试输出
  `failure_report.json`，没有可播放的 `mission_view.v1.json`。
- 本阶段不以演示动画时长冒充算法真实计算耗时。
- 本阶段不支持缺少地图展示坐标的任务二输出。

## 4. 方案选择

采用“独立任务二领域模型 + 复用现有地图能力”。

```text
CaseBundleV2 ──────────────┐
                           ├─→ MissionMapProjection → 地图/无人机/时间轴
MissionViewV1 → DynamicScene┘
```

不把任务二直接转换成 `CaseBundleV2`。直接转换会丢失 `eventTimeline`、`planDiff`、
`changeType`、计划状态、时间链和备选方案摘要，并导致任务二附加数据与任务一模型形成
两个并行真相来源。

也不建立完全独立的任务二地图工作区。独立工作区会重复地图、时间轴、图层偏好和交互
代码，并增加两个任务模式视觉与行为逐渐分裂的风险。

## 5. 前端模块边界

新增目录：

```text
src/features/dynamic-replanning/
├── missionViewSchema.ts
├── dynamicSceneSchema.ts
├── loadDynamicScene.ts
├── buildDynamicScene.ts
├── dynamicPlayback.ts
├── dynamicMapProjection.ts
└── dynamicMetrics.ts
```

各模块职责：

- `missionViewSchema.ts`：定义与 Python `MissionViewV1` 对应的严格 Zod Schema。
- `dynamicSceneSchema.ts`：定义场景目录、演示元数据和来源文件的契约。
- `loadDynamicScene.ts`：加载并校验基线、任务二视图、可选失败报告和来源记录。
- `buildDynamicScene.ts`：建立任务、资源、分配、航迹和事件索引，并完成跨文件一致性检查。
- `dynamicPlayback.ts`：纯函数式播放状态机，管理演示阶段、任务时间和播放控制。
- `dynamicMapProjection.ts`：把任务一或任务二模型投影成共享地图组件需要的数据。
- `dynamicMetrics.ts`：生成算法输出指标及可追溯的前后对比展示值。

任务一现有 `CaseBundleV2`、算例导入、存储和加载流程保持不变。任务模式选择属于工作台
界面状态，不写入 Kepler Redux 状态。

## 6. 场景数据组织

全局目录：

```text
public/data/task2/scenes/catalog.json
```

单个场景目录：

```text
public/data/task2/scenes/<scene-id>/
├── scene.json
├── baseline.bundle.json
├── mission_view.v1.json
├── failure_report.json
└── provenance.json
```

`failure_report.json` 只在 `PARTIAL_SAFE_FALLBACK` 场景中必需。

文件职责：

- `baseline.bundle.json` 还原事件发生前的任务一画面。
- `mission_view.v1.json` 是任务二结果的唯一业务数据入口。
- `scene.json` 只保存标题、说明、镜头、演示阶段时长和界面提示。
- `provenance.json` 保存任务二提交号、生成命令、生成时间、基线计划版本和输入输出
  SHA-256。
- `catalog.json` 保存场景顺序、显示名称、结果状态和目录入口。

`scene.json` 不得覆盖任务、资源、航迹、事件、指标、校验或计划状态。业务字段必须来自
任务二真实输出。

加载时必须验证：

- `schemaVersion` 为前端明确支持的版本；
- 基线与任务二视图的 `caseId` 一致；
- `activePlan.sourcePlanVersion` 与任务二生成过程记录的基线计划版本一致；
- 任务、资源、分配和航迹引用闭合；
- `provenance.json` 中的哈希与实际文件一致；
- `PARTIAL_SAFE_FALLBACK` 场景存在有效的 `failure_report.json`；
- 所有参与地图展示的路径包含有效 `mapPath`。

## 7. 离线数据生成流水线

`wrj-t2` 保存四组正式演示输入，包括基线引用、`runtime_state.json` 和
`dynamic_events.json`，并提供统一场景生成命令。每次生成必须：

1. 运行真实任务二 CLI；
2. 使用 Python `MissionViewV1` 模型校验输出；
3. 检查场景的预期计划状态和关键业务断言；
4. 记录任务二 Git commit、生成命令和输入输出哈希；
5. 将可发布文件写入明确的导出目录。

前端增加两个命令：

```text
npm run data:prepare-task2
npm run data:check-task2
```

`data:prepare-task2` 从任务二导出目录读取场景，使用前端 Schema 再次校验，复制发布文件并
生成 `catalog.json`。`data:check-task2` 在 CI 和提交前检查场景数据没有过期、被手工修改
或违反前端契约。

生成后的场景资产提交到前端仓库。现场演示只需静态文件，不依赖 Python、后端服务或网络。

## 8. 航迹时间投影

任务二 `MissionViewSegment.mapPath` 保存地图坐标，航段只提供 `startTimeSec` 和
`finishTimeSec`，未提供逐点时间。前端按相邻地图点的累计距离比例，在航段起止时间之间
生成逐点时间：

```text
pointTime = startTime + cumulativeDistance / totalDistance
            × (finishTime - startTime)
```

规则：

- 算法航段起止时间保持不变；
- 零长度多点路径按点序号均匀分配时间；
- 单点路径作为静态位置；
- 相邻航段边界使用后一个航段处理航向，避免重复点引起图标抖动；
- 插值结果只属于展示投影，不回写业务数据。

## 9. 页面布局

顶部栏增加任务模式与任务二场景选择：

```text
WRJ | [任务一 静态规划] [任务二 动态重规划]
     [场景：无人机失联 ▼] [重新播放] [方案状态：COMPLETE]
```

任务二主体继续使用左侧面板、三维地图、底部时间轴和详情抽屉：

```text
┌────────左侧面板────────┬──────────三维地图──────────┐
│ 场景说明                │ 事件位置、任务区域、无人机 │
│ 当前阶段                │ 基线航迹、重规划航迹       │
│ ● 基线执行              │ 告警光圈、变化动画         │
│ ● 动态事件              │                            │
│ ● 影响分析              │                            │
│ ● 重规划                │                            │
│ ● 新方案生效            │                            │
│ 资源状态 / 任务状态     │                            │
├────────────────────────┴────────────────────────────┤
│ ▶ 02:35 / 08:40  ━━━━━●━━━━  1×  事件标记  方案切换 │
└─────────────────────────────────────────────────────┘
```

交互规则：

- 切换任务模式不离开当前应用。
- 选择任务二场景后完成加载并停在起点，用户点击播放后才开始。
- 时间轴标记事件发生与新方案生效两个关键节点。
- 左侧阶段列表随播放自动推进，当前阶段高亮。
- 点击任务、无人机或变化航段继续使用现有详情抽屉，并增加事件影响与重规划变化字段。
- 用户手动操作地图后，当前轮播放停止自动镜头控制，但动画继续。
- 点击“重新播放”恢复默认镜头和自动镜头控制。

顶部方案状态使用任务二的三态语义：

- `COMPLETE`：完整新方案；
- `PARTIAL_SAFE_FALLBACK`：安全回退，不是完整方案；
- `FAILED`：无安全方案，仅用于不可播放的失败审计入口，不出现在首批四个场景中；
- 加载或契约失败：数据异常，不映射为任何算法状态。

## 10. 图层与视觉语义

固定变化图例：

- 灰色虚线：事件前原计划；
- 深灰实线：已飞或锁定航段；
- 青色：复用航段；
- 橙色脉冲：修改航段；
- 绿色生长动画：新增航段；
- 红色淡出：取消航段。

颜色映射以任务二 `changeType` 为权威。基线只用于提供事件前的原航迹几何，不参与推断
任务二结果状态。

受影响任务区域使用边框脉冲，不使用大面积高频闪烁。资源告警使用图标外圈与状态标签，
不只依赖颜色表达。`PARTIAL_SAFE_FALLBACK` 使用琥珀色状态横幅和明确文本，不能复用
成功方案的绿色表现。

## 11. 播放状态机

播放采用双时钟：

- 任务时钟使用算法任务时间，决定无人机位置和任务进度；
- 演示时钟控制告警、镜头、阶段高亮和航迹过渡。

统一阶段：

```text
READY
  → BASELINE_RUNNING
  → EVENT_ALERT
  → IMPACT_REVEAL
  → REPLAN_EXPLAINER
  → PLAN_TRANSITION
  → ACTIVE_PLAN_RUNNING
  → RESULT_HOLD
```

阶段行为：

1. `READY`：数据加载完成，停在起点。
2. `BASELINE_RUNNING`：任务时钟推进到事件时间，无人机沿基线飞行。
3. `EVENT_ALERT`：任务时钟停在权威事件时刻，镜头聚焦受影响对象。
4. `IMPACT_REVEAL`：依次高亮受影响任务、资源和未来航段。
5. `REPLAN_EXPLAINER`：展示影响分析、候选生成、安全校验和方案选择。这里只表示处理
   阶段，不展示或声称真实计算耗时。
6. `PLAN_TRANSITION`：旧未来航迹淡出，新航迹从当前状态向前生长。
7. `ACTIVE_PLAN_RUNNING`：任务时钟从 `activePlan.missionTimeSec` 恢复，新方案开始执行。
8. `RESULT_HOLD`：切换到全局视角并保留差异图层与结果指标。

暂停冻结两个时钟和所有阶段动画。拖动时间轴根据目标任务时间重建确定的地图状态；若拖到
事件前，显示基线；若拖到事件后，显示已提交的新方案。拖动不重播告警镜头。点击重新播放
才从 `READY` 重置完整叙事。

## 12. 首批四个场景

### 12.1 无人机失联

- 事件类型：`RESOURCE_LOST`。
- 失联资源变红、闪烁并冻结在事件位置。
- 其未执行未来航迹变成红色虚线并淡出。
- 受影响工作单元与侦察条带依次高亮。
- 接管资源出现青色外圈，新分配航迹向未完成区域生长。
- 必须断言失联资源在事件后不存在未来执行航段。

### 12.2 低油量返航

- 事件类型：`RESOURCE_LOW_FUEL`。
- 油量指示进入橙色告警。
- 资源按任务二决策完成当前安全部分或立即脱离，并生成返航航迹。
- 剩余工作单元转移给其他资源。
- 突出显示剩余油量、总完成率、总燃油和预计完成时间。

### 12.3 临时新增侦察区

- 事件类型：`NEW_TASK`。
- 新区域使用扩散边框出现。
- 新工作单元或侦察条带逐条显现。
- 负责资源高亮，新航迹从权威运行位置或基地向新区域生长。
- 突出显示任务数量、总完成率和预计完成时间。

### 12.4 硬截止无法满足

- 事件类型为 `TASK_LATEST_FINISH_CHANGED`。基线任务的 `deadlineType` 固定为 `HARD`，
  事件把 `latestFinishTimeSec` 提前到无法满足的时间。场景生成测试必须证明最终硬截止
  不可满足。
- 时间轴显示红色截止线，目标任务区域进入警告状态。
- 安全航段继续显示，必要返航路径生成。
- 未解决任务使用斜纹区域和 `UNRESOLVED` 文本。
- 结果必须是 `PARTIAL_SAFE_FALLBACK`，并展示对应失败原因。

## 13. 镜头与可访问性

- 每个场景只自动聚焦一次事件对象，并在结果阶段切换一次全局视角。
- 不连续旋转地图，不在场景切换时使用快速飞行。
- 用户操作地图后停止当前轮自动镜头控制。
- `prefers-reduced-motion` 下使用淡入淡出替代脉冲、快速生长和飞镜头。
- 状态、事件和变化类型同时使用文本、图形或线型，不只依赖颜色。

## 14. 异常处理

- 场景目录加载失败：任务二入口显示“场景目录不可用”，任务一继续工作。
- 单个场景校验失败：只禁用该场景，并显示具体校验原因。
- 文件哈希不一致：拒绝播放并提示场景数据可能被修改。
- 基线与任务二版本或引用不一致：拒绝合并展示。
- 部分安全回退缺少失败报告：数据包不完整，拒绝播放。
- 缺少地图路径：明确报错，不把本地米制坐标当成经纬度。
- 不使用空数组、默认成功状态或任务一数据静默替代损坏的任务二结果。

错误界面保留文件名、Schema 路径和简短原因；详细堆栈只在调试模式显示。

## 15. 测试策略

### 15.1 任务二侧

- 四个场景均通过真实引擎运行；
- 输出通过 Python 契约和跨文件校验；
- 场景结果状态符合预期；
- 失联、低油量、新任务和安全回退的关键业务断言通过；
- 固定输入重复运行产生确定的业务输出。

### 15.2 前端契约与适配

- Python Schema 与 TypeScript Zod Schema 使用同一批样例交叉验证；
- 验证场景目录、哈希和基线关联；
- 验证任务、资源、分配和航迹引用闭合；
- 验证路径距离时间插值及零长度、单点边界；
- 验证变化类型映射和指标来源。只有两侧同名同义的总燃油、完成时间等指标才展示增减
  对比；任务一覆盖率与任务二总完成率分别展示，不计算误导性的差值。

### 15.3 播放与界面

- 状态机的播放、暂停、拖动、重播和阶段跳转可确定复现；
- 任务模式切换不污染任务一状态；
- 场景选择后停在起点；
- 时间轴正确显示事件和方案切换标记；
- 地图图层按变化类型显示；
- 详情抽屉显示事件影响和重规划变化；
- 用户操作地图后停止自动镜头；
- 减少动态效果设置得到正确降级。

### 15.4 回归

- 任务一现有单元、组件和集成测试全部通过；
- 任务一算例导入、图层偏好、时间轴和无人机动画行为不变。

## 16. 验收标准

- 四个预制场景可在无 Python 服务、无后端和无网络条件下完整播放。
- 每个场景都能清楚看到事件前、事件发生、方案切换和事件后。
- 自动播放支持暂停、拖动和重新播放。
- 拖动与重播不会造成无人机跳到错误航迹或时间。
- `COMPLETE` 与 `PARTIAL_SAFE_FALLBACK` 的视觉与文本含义明显不同。
- 任务一原有算例、图层控制、导入和动画不受影响。
- 1366×768 下主要演示信息无需页面滚动即可看到。
- 所有业务字段均可追溯到真实任务二输出。
- 数据错误不会被静默降级为成功演示。

## 17. 实施范围与顺序

该设计可作为一个实施计划完成，建议按以下依赖顺序拆分任务：

1. 固化任务二四组场景输入与离线导出；
2. 建立前端 MissionView 和场景契约；
3. 完成场景加载、校验与数据准备脚本；
4. 建立共享地图投影和任务二图层；
5. 实现双时钟播放状态机；
6. 接入工作台模式、场景选择、阶段面板与状态横幅；
7. 实现四个场景的视觉脚本；
8. 完成跨仓库数据检查、回归和验收。
